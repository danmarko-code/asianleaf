## 2. Technology Constraints and Requirements

The stack was not chosen in the abstract; it was constrained by the conditions under which a student team builds and an association operates. On **hardware**, development ran on ordinary laptops with no dedicated graphics or server hardware, and the deployed workload is deliberately light: rendering is server-side, so a resident's low-end Android phone only parses HTML and a small stylesheet rather than executing a large client bundle. No component of the system requires a GPU, a message broker, or a background worker daemon, which is why reminders are triggered by an external scheduler instead of in-process timers. On **software**, the team standardized on Node.js 24 and npm 11 with Node 15-or-later PostgreSQL, because every dependency in `package.json` is installable from the public npm registry in one `npm install`, which also runs `prisma generate`. Proprietary or license-gated tooling was excluded: Next.js, React, Tailwind, Prisma, Zod, bcryptjs, and date-fns are all permissively licensed, so the project incurs **no licensing cost** and can be handed to the association without a subscription; the total **budget** therefore covers only hardware already owned and free-tier cloud services, with managed PostgreSQL the only cost that could arise if the association later moves off local hosting. On **network**, the design assumes intermittent mobile connectivity rather than reliable broadband: pages are server-rendered and form submissions are standard POST requests handled by server actions, so a resident on a weak mobile signal does not download a large single-page application before seeing the balance, and the officer's verification queue tolerates being opened, closed, and revisited without session loss because the session cookie persists for fourteen days. On **security**, the constraint was that the system would hold names, addresses, contact numbers, and payment references of real households, so the stack had to support HTTP-only cookies, cryptographic token generation, adaptive password hashing, and server-side authorization by default; bcryptjs at cost factor twelve, SHA-256 session-token hashing, and the `requireRole` guard on every mutation satisfy this without adding an external identity provider. On **compatibility**, the interface must work on the browsers residents already have, including mid-range Android devices and desktop Chrome or Edge in the association office, so the build targets ES2017 output with autoprefixed CSS and avoids experimental browser APIs; the PostgreSQL requirement is compatible with local installation and with managed providers named in the project documentation. Finally, on **team skill**, the members already worked in JavaScript and relational SQL, so investing in TypeScript, Prisma, and Tailwind leveraged existing knowledge instead of requiring a new language runtime; the resulting stack is small enough that any member can read an entire request path, from page component to server action to Prisma query, without specialist knowledge of a framework's internals. Each of these constraints maps back to approved requirements: the browser platform and mobile-first styling serve NFR-03, the hashing and authorization decisions serve NFR-01 and NFR-02, the relational constraints serve NFR-05, and the scheduler-driven job exists because NFR-06 requires an operational trigger that fails closed.

## 2. Development Approach Justification

The project follows an **iterative and incremental prototyping** model with Agile characteristics, and the commit history is the clearest evidence of that choice. The first increment (`dc6d0be`) delivered a vertical scaffold rather than a complete layer: application shells, a design system, a 377-line schema, a seed of demo data, and a health endpoint. That produced a running, clickable prototype in a single day, which is precisely the purpose of throwaway-to-evolvable prototyping: the association could react to something concrete before the expensive modules existed. Subsequent increments each closed one risk in the requirement set instead of attempting a big-bang delivery. `1edd6c3` added the authentication, payment, violation, and household-registration core. `ce978db` and `3ca8a0a` were short correction cycles driven by validation defects discovered while using that core. `f841d2a` removed an unnecessary field, supplied the GCash QR asset, and finalized the prototype surface. `04773c2` then reworked the registration architecture, deleting the self-registration and approval queue in favour of admin-created households, a revision that no waterfall plan would have anticipated because it came from observed usage. `6aa9a3d` removed email and one-time-password recovery in favour of administrator-controlled resets and added the reports module. `a711669` standardized vehicle types and plate validation.

Three properties of this workflow support short cycles. First, **increments are deployable**: because each slice includes its migration, action, and page, the system is demonstrable at every commit boundary, and a failed slice can be reverted without stranding unrelated work. Second, **feedback has a short path**: the seeded accounts (`admin`, `treasurer`, `maria.santos`, and others) let a reviewer reproduce any reported defect within seconds, and the redirect-with-message pattern makes the outcome of a revision visible on screen rather than in a log. Third, **revision is cheap by design**: schema-first migrations mean a domain correction such as removing `PARTIALLY_PAID` from `DueStatus` is a named, reviewable migration rather than a manual data edit, and centralized domain helpers mean a rule change such as the reminder de-duplication key is applied in one file. The verification protocol is deliberately manual because the deliverable is a prototype being evaluated for correctness of behaviour rather than a production service; the static gates (`lint`, `typecheck`, `build`) plus the twelve-point checklist give a repeatable regression pass that fits inside one laboratory session, which is the practical constraint that made a heavier automated suite unjustifiable at this stage. Each iteration was also bounded by the approved requirement baseline, so scope growth was expressed as a revision to a numbered requirement rather than as unplanned drift.

## 2. Priority Workflow

The workflow demonstrated by the prototype is the association's monthly money cycle: **a resident settles dues, an officer verifies the claim, and the outcome becomes visible in both the resident's record and the transparency data.**

It begins when the administrator opens `/admin/dues`, selects a billing month such as `2026-11`, and generates dues. The action reads every household identifier, builds one row per household at PHP 1,500.00 with a due date on the 5th, and inserts them with `skipDuplicates`, so a second press reports that dues were already generated rather than doubling the obligation. The resident then signs in at `/login` with a username and password; the server lowercases and pattern-checks the username, compares the bcrypt hash, confirms the account is `ACTIVE`, creates a hashed session, and redirects to `/app/dashboard`, where the unpaid due appears as a balance hero with its due date and a Pay-now control. On `/app/payments` the resident sees the HOA GCash card, including the seeded QR image and the account name and number, transfers the amount in the GCash application outside the system, and returns to submit the claim.

The submission is validated in four layers before anything is written. The form restricts the reference to 4–80 trimmed characters and the amount to a positive value no greater than 100,000; the browser blocks obviously malformed input; the server action re-parses the payload with Zod; and then the domain checks run in order. The due must belong to the caller's own household, must not already be `PAID` or `WAIVED`, and the requested amount must not exceed the outstanding balance computed from previously approved payments. Only then is a `Payment` row created with status `PENDING`, the method inherited from the channel, and the review fields left empty.

The treasurer then opens `/admin/payments`, compares the reference number against the actual GCash transaction history, and decides. Approval runs inside a transaction that stamps the payment `PAID`, generates a receipt number in the form `RCPT-2026-<six hex characters>`, recomputes the sum of approved payments for that due, flips the due to `PAID` only when the verified total covers the amount, and inserts a `PAYMENT_RECEIVED` notification carrying the receipt number. Rejection requires a reason between three and three hundred characters, stores it on the payment, and notifies the resident that the payment was not verified. Because the treasurer also records income and expense entries on `/admin/budget`, the collection decisions and the published ledger remain consistent, and the resident can confirm the association's published figures on the read-only `/app/budget`.

The **exception case** demonstrated alongside the happy path is the **duplicate reference number**. GCash reference numbers are unique in reality, so the schema declares `Payment.referenceNumber` unique. When the resident re-submits a reference already claimed, even against a different billing period, Prisma raises `P2002`, the action catches it, and the interface returns "That reference number was already submitted." with no row written and no effect on the balance. Two related guards are demonstrated in the same sequence: an amount exceeding the remaining balance is refused with the balance stated in the message, and a due that has already been settled or waived is refused with "That billing period is no longer open." All three failures are non-destructive, which is the property that matters: a mistyped reference can never create a second obligation, and a rejected or malformed claim leaves the due and the ledger exactly as they were.

## 1. Coherent Chapter 3 Narrative Draft

**CHAPTER 3 (CONTINUED) — SYSTEM DEVELOPMENT AND PROTOTYPING**

### 3.8 Technology Stack Selection

The technology stack of Asianleaf was selected against the approved requirement set rather than against novelty. The platform decision established a cross-platform web application rendered on the server through the Next.js App Router, so that a single artifact serves both the officer workspace and the resident workspace. This choice answers a structural property of the user population: officers perform their duties from desktop browsers in the association office, whereas residents reach the system from personal mobile phones, and a browser-delivered system accommodates both without application-store distribution or per-device installation. The programming language selected was TypeScript in strict mode on Node.js, because the domain is concerned with money and household identity; strict typing converts a schema drift, such as a misnamed payment status or due amount, into a compile-time failure rather than a runtime defect. The framework and library set comprises Next.js, React, Tailwind CSS, Zod, Prisma Client, bcryptjs, and date-fns. Server components and server actions removed the need for a separately authenticated programming interface, which reduced both the attack surface described in NFR-02 and the implementation burden on a small team, while Tailwind CSS with CSS-variable design tokens provided the responsive and dark-mode system required by NFR-03 without importing an unused component library. Zod serves as the single validation authority referenced by NFR-07, and its inferred types align the client hints with the server schema.

The database selected was PostgreSQL accessed through Prisma ORM, and the justification is traceable to NFR-05. The financial entities require exact decimal arithmetic, enumerated statuses, unique obligations per household and billing period, and referential actions that prevent deletion of posted payments; PostgreSQL supplies all four, and its partial unique index accommodates the vehicle-plate rule that exempts the shared unregistered placeholder. The development tooling consisted of Git with a GitHub remote, npm, ESLint, Prettier, Prisma CLI, and Prisma Studio. This arrangement was not incidental: the branch-per-feature workflow produced the commit history that this chapter uses as development evidence, and the combination of linting and type checking provides two complementary static gates. Hosting and infrastructure were deliberately left environment-driven. The application runs as a single Next.js server with secrets supplied through environment variables, and the reminder job is invoked externally against a bearer-protected endpoint. No deployment manifest is committed, which is an honest reflection of the prototype's status: the system is deployable, but the association's production hosting decision remains open and is recorded as such in the prototype boundary rather than presented as complete.

### 3.9 Development Approach and Environment

The project followed an iterative and incremental prototyping model. Its first increment established a complete vertical scaffold, comprising the application shells, the design system, the relational schema, seeded demonstration data, and a health endpoint, which produced a navigable prototype within a single working day. Each subsequent increment then closed one risk in the requirement set: authentication, payment submission and verification, violation notices, and household registration were delivered together as the first functional increment; two short correction cycles followed immediately, driven by validation defects discovered in use; a third cycle removed an unnecessary field and supplied the payment asset; and later increments reworked the registration architecture, replaced one-time-password recovery with administrative resets, added reporting and export, and standardized vehicle registration. The decisive evidence for the model is that the registration rework deleted approximately one thousand eight hundred lines of self-registration and approval-queue code that had appeared reasonable at design time but proved to generate unverifiable records and duplicate review work in practice. A waterfall sequence would have carried that defect into integration; an incremental model absorbed it as one bounded revision.

Three properties of the workflow sustained short cycles. Increments remained demonstrable, because each slice carried its own migration, server action, and page, allowing any commit boundary to be shown to the adviser or to association officers. Feedback remained cheap to obtain, because seeded accounts allow any reported behaviour to be reproduced in seconds and because every mutation communicates its outcome as an explicit notice or error string on the screen. Revision remained safe, because schema-first migrations record domain corrections as named, reviewable steps, and centralized domain helpers localize rule changes to a single file. Testing in this phase was a documented manual protocol rather than an automated suite. Every revision executed lint, type-check, and production build with the development server stopped, and then replayed a twelve-point verification checklist covering seed idempotency, duplicate rejection, dues regeneration, reminder de-duplication, payment approval, and feedback notification. The environment supporting this protocol consisted of an ordinary development laptop, Windows with a bash-compatible shell, Node.js 24 and PostgreSQL 15 or later, the pinned package set recorded in the project manifest, and browser-based device emulation from three hundred twenty to fourteen hundred forty pixels for responsive verification.

### 3.10 Prototype Scope and Interface Plan

The prototype implements twenty-four distinct screens and endpoints, each mapped to approved requirements. The authentication surface consists of the root router and the sign-in screen, both bound to FR-10 and to the credential protections of NFR-01 and NFR-02, together with an internal design guide that renders the complete primitive inventory for review. The officer workspace comprises the dashboard, the member directory, the add-member wizard, the member record with its tabbed sub-forms, the dues console, the payment verification queue, the violations register, the budget editor, the reports builder and its export endpoint, the feedback inbox, and the audit log. The resident workspace comprises the dashboard, the payments screen, the violations list, the profile, the read-only transparency report, and feedback. Two machine-facing endpoints complete the surface: a health probe and a bearer-protected reminder job. Each screen was specified by its inputs, its expected output, and its completion status, and no screen appears in the plan that is absent from the repository.

The workflow chosen to demonstrate the prototype is the monthly money cycle, because it exercises the largest number of requirements in one sequence. The administrator generates the billing period; the resident signs in, reads the balance and the GCash instructions, transfers funds outside the system, and submits a reference number; the treasurer verifies the reference and approves it; and the resident's record and the published ledger both reflect the verified outcome. Input validation occurs in four ordered layers along that path: browser constraints, server-side schema parsing, domain checks that the due belongs to the caller and remains open, and balance arithmetic that forbids overpayment. The exception case demonstrated is the duplicate reference number. Because the reference is unique in the schema, a repeated submission is refused at the database boundary and reported to the resident as a non-destructive error, leaving the due and the ledger untouched. Two adjacent guards are shown in the same sequence, namely the overpayment refusal and the closed-period refusal, so the demonstration proves that malformed or duplicated claims cannot create obligations. The prototype boundary was documented honestly in three classes. Fully functional are authentication, household records, due generation, threshold reminders, manual verification, violation notices, transparency reporting, feedback, reports and export, password reset, and the audit trail. Simulated are outbound messaging through a console provider, verification performed by reading the external GCash application, the static QR asset and placeholder account number, the fixed billing constants, and the external scheduling of the reminder job. Deferred are carrier-delivered messaging, automated payment reconciliation, receipt upload, configurable billing rules, notification fan-out for notices, automatic posting of payments into the ledger, paginated exports, threaded feedback, self-service credential recovery, security-event logging, and automated testing with a deployment pipeline.
